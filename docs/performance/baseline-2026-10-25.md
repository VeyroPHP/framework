# Performance Baseline, 2026-10-25

This is the first measured baseline. It describes **one development laptop**, not production hardware, and compares VeyroPHP only with itself and with plain PHP. **No comparison with other frameworks has been measured, so none is claimed.**

Raw data:

- In-process micro-benchmarks: [results/2026-10-25-i7-7700HQ-opcache-off.json](../../bench/results/2026-10-25-i7-7700HQ-opcache-off.json)
- HTTP and bootstrap measurements: [results/2026-10-25-http-apache-i7-7700HQ-opcache-off.txt](results/2026-10-25-http-apache-i7-7700HQ-opcache-off.txt)

### With opcache enabled (2026-10-26)

Same machine and method, after enabling opcache in Apache with default settings ([raw](results/2026-10-26-http-apache-i7-7700HQ-opcache-on.txt)):

| URL | Requests/s | p50 | p95 | p99 | vs. opcache off |
| --- | ---: | ---: | ---: | ---: | ---: |
| Plain PHP `echo "Hello"` | 3,208 | 2 ms | 15 ms | 17 ms | within run-to-run noise |
| VeyroPHP welcome page | **1,327** | 6 ms | 17 ms | 23 ms | **4.2×** |
| VeyroPHP 404 | **1,274** | 7 ms | 17 ms | 29 ms | **4.3×** |

This confirms finding 2: most of the opcache-off cost was compiling the 67 files on every request.

## Findings

1. **Bug found by benchmarking: 5 seconds per request for HTTP/1.0 clients.** The response always declared HTTP/1.1, so Apache kept HTTP/1.0 connections open until its keep-alive timeout: 1.99 requests/s with `ab`. The kernel now answers in the request's protocol version, and a regression test covers it.

2. **Per-request cost is dominated by cold start, not by request handling.** A warm second request inside the same process takes 0.23–0.28 ms, and the kernel itself takes about 13 µs. A cold process takes about 20 ms, spread across loading and compiling 67 files (config and `.env` 4 ms, creating the kernel 5 ms, first request 6–7 ms).
   - An authoritative Composer classmap changed this by only about 4%.
   - Opcache in CLI file-cache mode reduced it by about 15%.
   - Shared-memory opcache in Apache (measured on 2026-10-26, see above) raised throughput from 315 to 1,327 requests/s. A config cache and container compilation remain possible optimizations if profiling with opcache shows they matter.

3. **Query builder overhead is about 15 µs per query** compared with a reused raw PDO statement: SQL compilation about 5 µs, a new prepare about 4 µs, and the rest from building and cloning the builder in `first()`. Statement caching could remove the prepare cost. For queries that touch disk or the network, the overhead is small relative to the query.

4. **Dynamic routes are matched linearly.** The last of 100 dynamic routes takes about 38 µs, while static routes take about 1 µs regardless of count. Combining route regexes into chunks (as FastRoute does) is a known optimization, if real applications reach hundreds of dynamic routes.

5. **View rendering costs about 73 µs without opcache**, because the template is compiled on every render. Opcache should remove most of this; not yet measured.

6. Plan items not benchmarked yet: ORM with eager loading and cached responses (ORM and cache do not exist yet).

## Limitations

- One laptop, with background applications and antivirus running; numbers vary between runs (see min–max).
- `ab` ran on the same machine as Apache, so the client competes with the server for CPU.
- Windows + mod_php (ZTS) behaves differently from Linux + PHP-FPM, the usual production setup.
- Opcache was off for the micro-benchmarks (CLI) and for the first HTTP table; the second HTTP table has opcache on in Apache.
