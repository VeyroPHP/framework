# Performance Recheck, 2026-10-26 (Phase 8)

Goal: compare the current code with the [Phase 4 baseline](baseline-2026-10-25.md) after Phases 5–7 added the ORM, security middleware, console and more providers.

**First attempt: inconclusive.** (A second attempt on a quieter machine, below, gave stable HTTP results.) During the run the laptop had only 0.5–0.8 GB of 16 GB RAM free (browser and several editor windows open), and repeated runs of the same benchmark differed by up to 3×. The numbers below are recorded as measured, but they must not be read as the framework's speed. A clean re-baseline needs a quiet machine.

Raw data: [bench/results/2026-10-26-i7-7700HQ-opcache-off-phase8.json](../../bench/results/2026-10-26-i7-7700HQ-opcache-off-phase8.json) and [run 2](../../bench/results/2026-10-26-i7-7700HQ-opcache-off-phase8-run2.json).

## What can be compared: ratios within the same run

Ratios against code that VeyroPHP does not touch (raw PDO, PSR-7 objects) cancel out most of the machine noise.

| Ratio | Phase 4 | Run 1 | Run 2 | Reading |
| --- | ---: | ---: | ---: | --- |
| Query-builder read / raw PDO (prepare each time) | 0.33 | 0.34 | 0.32 | No change in the database layer |
| Kernel minimal route / PSR-7 request+response | 0.61 | 0.54 | 0.50 | Kernel possibly 10–18 % slower |
| Kernel + 3 middleware / kernel minimal | 0.78 | 0.81 | 0.75 | Middleware cost unchanged |

The kernel now detects the base path, prefixes local redirects and sets the response protocol version on every request (Phase 6). A cost of this size is plausible, but within this noise it is not proven.

## HTTP through Apache (opcache on)

| URL | Phase 4 | This session (repeated runs) |
| --- | ---: | --- |
| Plain PHP `echo` | 3,893 req/s | 3,667 req/s |
| Welcome page | 1,327 req/s | 232, 671, 804, 889, 904 req/s |
| Login page (creates a session per request) | not measured | 36 req/s, p99 4.5 s |

Plain PHP is within 6 % of Phase 4, so Apache itself was not slow. The welcome page varied by almost 4× between consecutive runs.

In-process profiling with opcache (CLI, 200 iterations, median) puts the welcome page at about 1.5 ms for booting the application and 0.6 ms for handling the request, so the framework work per request is small. With the CLI numbers, Apache at concurrency 1 took 6.7 ms per request, so most of the time is spent outside the framework code (Apache, PHP startup, memory pressure).

The login page creates a new session file on every request without a cookie, which on this Windows laptop (antivirus scanning new files) is slow. This is a worst case: real visitors reuse their session.

## Findings that led to changes

- **Session files were never cleaned up.** Expired file-cache entries were only deleted when read; the login benchmark alone left about 2,000 session files. Added `FileStore::prune()`, `Cache::prune()` and `php veyro cache:prune` (see the [deployment guide](../deployment.md)).

## Third attempt: 4.1 GB free (browser and other editor windows closed)

Raw data: [quiet run c](../../bench/results/2026-10-26-i7-7700HQ-opcache-off-phase8-quiet-c.json), [quiet run d](../../bench/results/2026-10-26-i7-7700HQ-opcache-off-phase8-quiet-d.json).

| URL | Phase 4 | 3.4 GB free | 4.1 GB free |
| --- | ---: | ---: | ---: |
| Plain PHP `echo` | 3,893 | 2,609 / 2,733 | 3,347 / 3,254 |
| Welcome page | 1,327 | 839 / 865 / 886 | 866 / 890 / 870 (p50 9 ms, p99 52–56 ms) |

With more free memory plain PHP recovered (−15 % against Phase 4), but the welcome page stayed at about 870 requests/s (−34 %). The welcome page is limited by the work PHP does per request, not by memory, so dividing by plain PHP was not a valid correction. **The framework's per-request cost has grown by roughly 20 % since Phase 4.**

The micro-benchmarks agree:

| Ratio | Phase 4 | Run a | Run b | Run c | Run d |
| --- | ---: | ---: | ---: | ---: | ---: |
| Kernel minimal route / PSR-7 request+response | 0.61 | 0.57 | 0.55 | 0.46 | 0.54 |
| Query-builder read / raw PDO reused statement | 0.086 | 0.075 | 0.085 | 0.082 | 0.093 |

The database layer is unchanged; the kernel is 10–25 % slower relative to PSR-7 (runs still vary by up to 40 % because microsecond operations depend on CPU frequency on this laptop).

## Conclusion

A real regression of about 20 % per request since Phase 4, in the HTTP path, not the database layer. Likely contributors, all added after Phase 4 and run on every request: loading more config files (no config cache; `ConfigServiceProvider` was the largest bootstrap cost in profiling), more providers and middleware (`TrustProxies`, `SecurityHeaders`, sessions), the welcome page's `opcache_get_status()` call, and the kernel's base-path and redirect handling. Next step: profile one request with these switched off one at a time, then decide what to optimize (for example a config cache). Absolute numbers still need a machine with a fixed CPU frequency.

## Cause found: the development autoloader

The starter app used Composer's default autoloader, which looks up every class on disk (PSR-4) at runtime. One welcome-page request loads 112 PHP files (65 from the framework), and on Windows each lookup through the starter app's `vendor/veyrophp/core` junction is a filesystem call. Phases 5–8 added classes, so the lookups grew.

| Welcome page, same session | Requests/s |
| --- | --- |
| Default autoloader (PSR-4 lookups) | 820, 916 |
| Optimized autoloader (`composer dump-autoload -o`, classmap) | 1,021, 1,251, 1,289 |

With the classmap the welcome page is back at the Phase 4 level (1,327) although every request now also starts sessions-capable middleware, security headers and more providers. The "regression" was the development autoloader, not slower framework code. Production deployments already use `--optimize-autoloader` (deployment guide); the starter app now sets `"optimize-autoloader": true` in `composer.json`, as Laravel does, so development matches production. A config cache could still save about 0.5 ms per request and is noted for later.

## Compared with Laravel 12 (2026-10-26)

Same machine, same Apache + mod_php + opcache, both in production mode with caches built (Laravel 12.70.1: `artisan optimize`, optimized autoloader; VeyroPHP: `config:cache`, optimized autoloader). `ab -n 2000 -c 10`, the two frameworks run alternately, three rounds, 0 failed requests in every run.

| Request | VeyroPHP | Laravel 12 | Plain PHP `echo` |
| --- | --- | --- | --- |
| Route returning `Hello` (no session in either) | 1,512–1,548 req/s, p50 6 ms | 796–811 req/s, p50 12 ms | 2,932–3,109 req/s |
| Welcome page | 1,607–1,718 req/s, p50 5–6 ms | 377–414 req/s, p50 15–16 ms, p99 up to 644 ms | |

How to read it:

- The `Hello` route is the fair comparison: VeyroPHP is about **1.9× faster** there, because it loads and runs less code per request. Plain PHP (about 3,000 req/s) is the ceiling on this machine; VeyroPHP reaches about half of it, Laravel about a quarter.
- The welcome pages are not equal (Laravel's is 80 KB with session cookie encryption, VeyroPHP's 6.9 KB), so the 4× gap there overstates the difference. Laravel's welcome page in a subfolder install returned 405 for `/`, so `/index.php` was measured.
- In real applications most time goes to database queries and the work itself, so the gap shrinks. Laravel also offers Octane (the application stays in memory), which VeyroPHP does not have yet; VeyroPHP also has fewer features.
- Absolute numbers depend on this Windows laptop; only the ratios are meaningful.

The temporary Laravel project and benchmark routes were removed afterwards.
