# ADR 0022: Mail

- Status: Accepted
- Date: 2026-10-26

## Context

Laravel parity item 3. Laravel sends mail through Symfony Mailer. VeyroPHP has no Symfony runtime dependency, and password reset and email verification (item 5) need mail.

## Decisions

- **Own SMTP client and MIME builder** instead of Symfony Mailer or PHPMailer. SMTP submission and MIME generation are small, well-specified protocols; owning them keeps the framework free of a large dependency and lets the security rules below be enforced in one place. The cost is that only SMTP is built in; providers' HTTP APIs are added through the `Transport` interface.
- **Secure by default**:
  - `tls` (STARTTLS) never falls back to plain text when the server does not offer it (no downgrade).
  - Certificates are verified unless explicitly turned off.
  - Credentials are refused over unencrypted connections except to localhost.
  - Every address, name, subject, header value and attachment name is checked for line breaks and control characters (header injection). Headers the builder writes itself cannot be overridden.
- **MIME output** is 7-bit only, so no server needs 8BITMIME or SMTPUTF8:
  - quoted-printable UTF-8 bodies
  - base64 attachments
  - RFC 2047 encoded words for non-ASCII header text, sized so lines stay within 78 characters
  - RFC 2231 for non-ASCII attachment names
  - boundaries starting with `=_`, which cannot occur in quoted-printable or base64
  - Bcc never written
  - CRLF only
- **Plain-text part generated from HTML** when only HTML is given, because HTML-only mail scores worse with spam filters.
- **Views** are rendered by the Mailer (`view()`, `textView()`), using the normal escaping.
- **One connection per message.** Simple and robust; connection reuse can come with queues, where many messages are sent in a row.
- **Logging**: metadata only (mailer, Message-ID, recipient count, time), never addresses or content. The `log` transport is the deliberate exception for development and logs the decoded text body so links can be used.
- **Addresses must be ASCII** (domains in punycode). Non-ASCII local parts need SMTPUTF8, which many servers lack.
- Not supported yet: inline images (`cid:`), DKIM signing by the framework (providers sign), connection reuse, queued mail (item 4).

## Verified

- `SmtpTransportTest` (17 tests) runs against a scripted SMTP server in a child process over real sockets:
  - plain delivery with dot-stuffing restored byte for byte
  - STARTTLS and implicit TLS with a generated certificate checked against a CA file
  - an untrusted certificate refused
  - `verify_peer=false`
  - no downgrade when STARTTLS is missing
  - AUTH PLAIN and LOGIN
  - 535 with no password in the message
  - 550 recipient
  - unsupported mechanisms, silent server (timeout), closed connection, refused connection
  - invalid settings
  - a full message through the `Mailer` with Bcc in the envelope only
- `MessageTest` (24 tests): header injection, encoding of Hindi subjects and names (whole message 7-bit, no line over 78 characters), multipart structure, attachments byte for byte, HTML-to-text.
- `MailerTest` (14 tests): views, Mailables, logging without personal data, events, the service provider and custom transports.
- Console tests for `make:mail` (the generated class and view send a message) and `mail:test`.

Found while testing:

- The first version put a 72-character encoded word after `Subject: `, making the line 81 characters long. Encoded words are now sized by their position.
- A test helper blocked on the server's stderr pipe and looked like a Windows socket problem; it was the test.

**Verified against Mailpit 1.32.0** (2026-10-26, with the owner's permission). Mailpit ran locally with STARTTLS required and a self-signed certificate. The framework's `SmtpTransport` (encryption `tls`, certificate checked against a CA file, AUTH) sent one complex message, and Mailpit's independent MIME parser read every part correctly:

- a folded Hindi subject; Hindi From/To names; a quoted Cc name
- a Bcc recipient, delivered but not in the message
- HTML and the generated text part (with link URLs)
- a line starting with a dot
- a binary PDF, byte for byte
- an RFC 2231 Hindi attachment name
- a Hindi custom header

Mailpit's HTML compatibility check reported 100%.

Found there: a Hindi display name followed by its address, and long non-ASCII attachment names, produced lines over 78 characters (valid, under the 998 limit, but against the recommendation). Names are now folded before `<address>`, and attachment names use RFC 2231 continuations (`filename*0*`, `filename*1*`). A test checks that every line stays within 78 characters and that the continuations rejoin to the exact name, and Mailpit then reported no long lines.

A real mail provider has not been tried (needs the owner's account).
